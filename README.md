# LIB COWORK — 사서·AI 협업 청구기호 부여 데모

대학도서관에 새 책이 들어오면 사서가 청구기호(852 ▼h)를 매긴다. 이 데모는 실제 편목(cataloging) 업무 화면을 그대로 재현하고, 그 안에서 AI가 청구기호 후보와 근거를 제시하는 흐름을 보여준다.

2026 서강대학교 생성형 AI 아이디어 공모전 우수상 (sogang renAIssance 팀).
원본 저장소: https://github.com/HAICoLab/sogang_renAIssance

**데모 보기:** https://lilmosy.github.io/lib-copilot-demo/library_system.html

## 무엇을 하는가

사서는 새 책 한 권마다 같은 검색을 손으로 되풀이한다. 업체가 붙인 082 번호를 본교 서가에서 확인하고, 종합목록에서 타대학 분류를 세고, 다시 본교 서가와 대조하고, 책소개를 찾아 읽는다. 판단은 사서의 암묵지에 기대 있어 사람마다 갈린다.

AI-search는 이 과정을 한 번에 돌린다.

1. 책소개 API와 업체 082 번호·종합목록 타대학 분류·본교 장서 키워드로 후보 서가를 모은다.
2. 후보 서가마다 본교에 실제 꽂힌 도서를 읽고, 주제·관점과 자료 성격·용도 두 축으로 적합도를 채점한다.
3. 1순위가 기준을 넘고 2순위와 충분히 벌어지면 추천하고, 아니면 근거와 함께 사서에게 넘긴다.

쉬운 책은 AI가 끝내고, 갈리는 책만 사람이 본다.

## 화면

- **서지** — 본교 장서를 서명·저자·청구기호·키워드·ISBN·제어번호로 검색.
- **종합목록** (시작 화면) — KERIS 종합목록. 책을 고르면 대학별 소장·분류기호가 나오고, 검색해 가져온 책은 목록에 쌓인다.
- **편목** — 청구기호가 없는 신착도서 대기열. 책을 열고 AI-search를 누르면 후보·점수·근거가 나오고, 후보를 클릭해 852에 넣고 저장한다.
- **기각사례** — AI 추천이 사서의 최종 판단과 달랐던 사례.

화면 왼쪽 아래 사용법 패널에 둘러보는 순서가 있다.

## 이 저장소는 정적 배포판이다

원본 데모는 로컬 Python 서버가 1.3GB 장서 DB를 조회하고 LLM을 실시간 호출한다. 이 저장소는 서버 없이 GitHub Pages에서 그대로 돌아가도록 데이터 공급만 바꾼 것이다. 화면과 동작 로직은 원본과 같다.

| 원본 | 이 저장소 |
|---|---|
| 서버가 장서 DB 조회 | 장서 DB 부분집합(14만 건)을 브라우저 안 SQLite([sql.js](https://sql.js.org))로 열어 같은 SQL 실행 |
| LLM 실시간 호출 | 파이프라인을 한 번 실행해 저장한 결과 JSON (편목 대기열 5건) |

방문자가 어떤 버튼을 눌러도 외부 API는 호출되지 않는다.

## 로컬에서 보기

```
python3 -m http.server 8000
# http://localhost:8000/library_system.html
```

`file://`로 직접 열면 데이터 파일을 읽지 못한다.
